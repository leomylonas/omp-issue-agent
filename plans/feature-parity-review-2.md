Date: 2026-09-18

Authoritative specification: [`plans/issue-agent.md`](issue-agent.md).

Method: four independent, parallel evidence-backed audits (configuration/providers/context, observability/deployment/CI, security, and workflow/invariants — the last performed directly by the coordinating session) at maximum reasoning depth, each required to execute `dotnet build`/`dotnet test` and, where a claim was executable, a real throwaway reproduction (live `HttpListener`/`Dns`/`SslStream` servers, OTel Prometheus scrapes, `helm template`, `docker compose run`). ## 0. Verdict

**Round 1's remediation is real but incomplete, and it introduced several new defects.** Of the 51 round-1 findings, the large majority hold up under adversarial re-verification. But four claims in round 1's §11 "Remediation status" do not hold in production, each independently confirmed by at least one dedicated audit and, for the two most severe, re-verified directly by this session against real code and a real executable reproduction:

- **H2 is not fully fixed**: Octokit's primary `GitHubClient` — the one used for every issue/comment/label/PR operation — is constructed with no custom handler and therefore ignores the configured `TlsTrust` entirely. Only the four auxiliary HTTP clients (GraphQL, timeline, both attachment clients) were wired.
- **M12 is not fully fixed**: `GitLabProvider.ToLinkedRepository` synthesizes a `RepositoryRef.Id` of the shape `"gitlab/{projectId}"` that `GitLabProvider.GetIssueAsync`/`GitLabApiClient` cannot consume as a project identifier — every cross-project GitLab issue link 404s.
- **H16 is not fixed**: the Telegram sink's `BaseAddress` change did not fix the underlying defect. A real Telegram bot token (`<digits>:<hash>`) makes the interpolated relative path parse as an absolute URI with an unsupported scheme; `PostAsJsonAsync` throws `NotSupportedException` for every message, on every real token.
- **M16 is not fixed**: `Activity.Current` is provably `null` at the one line that sets `CorrelationId`, in every real dispatch path. The fix compiles, is exercised by no test, and is a complete no-op in production.

Beyond these four, this round found a further ~25 medium/low defects, several of them **new regressions introduced by round-1's own fixes** (the trust validator now rejects legitimate `§7` inheritance; the new global retry policy retries non-idempotent POSTs and applies uncapped server-controlled delays; the new `ObservableGitProvider` enumerable path mis-measures provider duration/request counts for every paginated call; decorator `catch (Exception)` blocks count ordinary cancellation as a provider/Git/OMP failure). None of the round-2 findings are credential-exfiltration-class; the worst outcomes are silent notification loss, unusable telemetry/correlation, SSRF against internal/cloud-metadata endpoints via DNS rebinding or redirects, non-rolling Kubernetes config updates, and durable canonical-comment data corruption for a specific (plausible) input shape.

Do not treat round 1's §11 as closed. The four "not fixed" items above and the High/Medium items in §2 below should gate before this is called done.

## 1. Method note: which fixes were independently re-executed by the coordinating session

Two claims were re-derived from first principles by the coordinating session, independent of the delegated audits, before any audit result was read:

- **M16 CorrelationId no-op**: traced the full call chain `Worker.ExecuteAsync → PollingScheduler.PollOnceAsync → WorkflowDispatcher.ExecuteAsync → DispatchInitialPlanningAsync/DispatchExistingAsync` and confirmed by `grep -rn StartActivity src/` that no `ActivitySource.StartActivity` call exists anywhere before the `Activity.Current?.SetTag(...)` line.
- **L3 canonical-comment corruption**: built a throwaway console app referencing `IssueAgent.Context.csproj` and round-tripped `["First.", "", "Third."]`, `["   "]`, and `["Trailing newline.\n"]` through `Render`/`Parse`, reproducing exact corruption before any audit report was read.

Both were then independently confirmed a second time by dedicated audits using their own methodology, and a third finding (H16 Telegram) and the SEC-R2-001 Octokit gap were each re-verified a second time by the coordinating session directly (a fresh `dotnet run` reproduction for Telegram; a direct code read for Octokit and the GitLab `RepositoryRef.Id` gap). This cross-validation is why these four are reported with high confidence.

## 2. Findings, severity-ordered

### High

#### H2-gap — Octokit's primary GitHub REST client never applies the configured `TlsTrust`
- **Spec**: §9 ("Additional CAs must be loaded in-process for .NET HTTP and libgit2 … Centralize TLS semantics").
- **Location**: `src/IssueAgent.Providers.GitHub/GitHubProviderFactory.cs:29-32` — `new GitHubClient(new Octokit.ProductHeaderValue("IssueAgent"), configuration.ApiBaseUri) { Credentials = credentials }`. No `IHttpClient`/`Connection`/handler override is supplied, so Octokit falls back to its own internal `HttpClientAdapter` over a bare `HttpClientHandler` with plain OS trust. Contrast the same factory's `graphQlHttpClient`/`timelineHttpClient`/both attachment clients, which correctly go through `CreateHttpClient(configuration.TlsTrust, …) → TlsHttpHandlerFactory.Create(tlsTrust)`.
- **Verified** by direct code read (coordinating session) and by the security audit's evidence walk of every Octokit call site (`Issue.Get`, `Issue.Comment.Create/Update/GetAllForIssue`, `Issue.Labels.*`, `PullRequest.Create/Get/GetAllForRepository`, `Issue.GetAllForRepository`).
- **Failure scenario**: an operator sets `tls.mode: pinned` (or `systemPlusAdditionalCa` for a private-CA GHES instance) specifically to defend the GitHub token against a MITM presenting a CA-trusted-but-not-pinned certificate — a corporate TLS-inspecting proxy, or a compromised/misissued intermediate. That protection covers GraphQL review-thread reads and attachment downloads only; every issue fetch, comment post, label change, and PR creation — the traffic carrying the bearer token on essentially every workflow turn — goes out over plain system trust regardless of the configured mode.
- **Impact**: security (token exfiltration / response tampering under an active MITM position); also breaks provider parity — GitLab's hand-rolled client (`GitLabProviderFactory.cs:14`) is correctly wired end-to-end, so the same `tls.mode: pinned` configuration behaves completely differently per provider.
- **Smallest safe correction**: construct `GitHubClient` with a custom `Connection`/`IHttpClient` wrapping `Octokit.Internal.HttpClientAdapter` built from `TlsHttpHandlerFactory.Create(configuration.TlsTrust)`, so every Octokit call shares the configured handler.

#### M12-gap — GitLab cross-project related-issue traversal is structurally broken
- **Spec**: §14 ("Follow/read provider-native relationships … Read related issue title, description"), §4, §26.
- **Location**: `src/IssueAgent.Providers.GitLab/GitLabProvider.cs:235` (`link.ProjectId.ToString(...) == repository.Id`) and `ToLinkedRepository` (`GitLabProvider.cs:301-315`, synthesizes `new RepositoryRef($"gitlab/{link.ProjectId}", owner, name)`), consumed by `GetIssueAsync` (`GitLabProvider.cs:76` → `client.GetIssueAsync(repository.Id, ...)` → `GitLabApiClient.cs:31`, `projects/{Encode(projectId)}/issues/{issueIid}`).
- **Verified** independently twice: the config/providers audit executed a live `HttpListener` reproduction under both supported `Id` conventions (numeric and `owner/repo` path) and got `InvalidOperationException: GitLab issue N was not found` (404) for every cross-project link; the coordinating session independently confirmed by reading `GetIssueAsync`'s direct use of `repository.Id` as the literal GitLab API path segment and `ToLinkedRepository`'s `"gitlab/{projectId}"` synthesis, which is not a valid GitLab project identifier under either convention.
- **Failure scenario**: a GitLab repository configured with either supported `Id` shape; a maintainer adds "relates to #42" (a different project) on the assigned issue. `RelatedIssueTraversalDepth` defaults to 1 (§14 "one hop by default"), so `AgentContextBuilder.TraverseRelatedIssuesAsync` runs, `GetIssueAsync` 404s, and the exception escapes `BuildAsync` — planning never starts for that issue. `GetIssueRelationshipsAsyncMapsGitLabLinkTypes` (the only test touching this path) only passes because its fixture sets the repository `Id` to the numeric project id and every link to the same project, so `linkedRepository` never actually takes the `ToLinkedRepository` branch.
- **Impact**: user-visible — any GitLab issue carrying a cross-project link is permanently unplannable until the link is removed or `RelatedIssueTraversalDepth` is set to 0. Cycle detection (`visited` keyed on `relationship.Repository.Id`) is also unsound, since the same project can appear under both its configured id and its synthesized `gitlab/{id}` alias.
- **Smallest safe correction**: stop overloading `RepositoryRef.Id` as the GitLab API project identifier. Give `GitLabProvider` an explicit project-identifier projection derived from `link.WebUrl` (matching how `GitHubProvider.cs:292` already derives owner/name from the timeline payload for exactly this reason) and keep `Id` as the workspace/correlation key only.

#### H16-gap — Telegram sink throws for every real bot token
- **Spec**: §28 (notification fan-out must deliver), §25 ("explain and notify" on human-intervention states), §33.
- **Location**: `src/IssueAgent.Notifications/TelegramNotificationSink.cs:19` — `httpClient.PostAsJsonAsync($"bot{botToken}/sendMessage", ...)`, composed with `BaseAddress = new Uri("https://api.telegram.org/")` at `src/IssueAgent.Host/Program.cs:51-55`.
- **Verified directly by the coordinating session** with a fresh `dotnet run` reproduction (`/tmp/telegram_uri_test`, since deleted): a real-shaped token `123456789:AAHdqTcvAKrOexampleTokenText` makes the interpolated string `bot123456789:AAHdqTcvAKrOexampleTokenText/sendMessage`, which `Uri`/`HttpRequestMessage`'s string constructor parses as an **absolute** URI (scheme `bot123456789`, matching RFC 3986's `ALPHA *(ALPHA/DIGIT/+/-/.)` scheme grammar) — `BaseAddress` is never consulted. Confirmed:
  ```
  IsAbsoluteUri = True
  Scheme = bot123456789
  SEND EXCEPTION: NotSupportedException: The 'bot123456789' scheme is not supported.
  ```
  Every real Telegram bot token has exactly this `<digits>:<hash>` shape (Telegram's own documented token format) — this is not an edge case, it is the only shape real tokens take. `tests/IssueAgent.Notifications.Tests/TelegramNotificationSinkTests.cs` uses the colon-free literal `"test-token"`, which never triggers the absolute-URI parse, so the suite is structurally blind to the defect.
- **Impact**: with Telegram configured, every notification (plan-ready, human-action-required, failure) fails permanently; `FanOutNotifier` exhausts its 3 retries on a non-transient error and only a `NotificationFailures` counter/warning records it. §25's "explain and notify" obligation silently never reaches a human.
- **Smallest safe correction**: `PostAsJsonAsync($"/bot{botToken}/sendMessage", ...)` (leading slash forces relative-to-`BaseAddress` resolution — verified to work); change the test token to a colon-bearing shape so the regression is defended going forward.

#### M16-gap — `CorrelationId` is never populated in production; the fix is a no-op
- **Spec**: §29 ("log context must include CorrelationId … easy to query all logs for one issue/workflow"), §30 ("WorkflowId correlates traces across days of human review").
- **Location**: `src/IssueAgent.Host/WorkflowDispatcher.cs:85,105` — `Activity.Current?.SetTag(LogContextFields.CorrelationId, Activity.Current?.TraceId.ToString() ?? Guid.NewGuid().ToString("N"));` is the first statement of both dispatch methods.
- **Verified three times independently** (coordinating session via call-chain trace + repo-wide grep; the observability audit via the same trace plus an executable async-iterator-leak refutation; the config/providers audit's H13 check confirmed `ObservableGitProvider`'s own activity does not leak into or precede this call either). Exhaustive: `Worker.ExecuteAsync` → `PollingScheduler.PollOnceAsync`/`DiscoverRepositoryAsync` → `WorkflowWorkerPool.RunWorkerAsync` → `WorkflowDispatcher.ExecuteAsync` starts **no** `Activity` anywhere in that chain before the `SetTag` line runs. Since `Activity.Current` is `null`, `?.SetTag(...)` is a silent no-op and `Guid.NewGuid()` is computed and immediately discarded — never attached to anything, never logged.
- **Secondary defect discovered while confirming this**: even where Activities *do* start later (Git/LFS/OMP operations via `IssueAgentActivitySource`), no caller ever passes a non-null `workflowId` argument, so no span in the system ever carries a `WorkflowId` tag either — half of `ActivityLogEnricher`'s allow-list (`WorkflowId`, `CorrelationId`, `IssueNumber`, `PullOrMergeRequestNumber`, `Component`, `OmpEventType`) is permanently dead code.
- **Impact**: the entire §29/§30 cross-log/cross-trace correlation story does not exist in production. No test would catch this — `tests/IssueAgent.Host.Tests` has no `WorkflowDispatcherTests`/`PollingSchedulerTests`, and no test anywhere asserts a `CorrelationId` value.
- **Smallest safe correction**: start one ambient `Activity` per dispatched unit of work (e.g. `using var activity = IssueAgentActivitySource.Source.StartActivity($"workflow.{kind}")` at the top of `WorkflowDispatcher.ExecuteAsync`), set `CorrelationId`/`IssueNumber`/`Repository` on it, and thread the resolved `WorkflowId` into every `Start*` helper once it is known.

### Medium

#### M4-gap — SSRF filter has live IP-range bypasses and does not survive redirects
- **Spec**: §15 ("download direct-file links … do not crawl").
- **Location**: `src/IssueAgent.Context/AttachmentPipeline.cs:146-166` (`IsUnsafeDestination` — misses `0.0.0.0`/`IPAddress.Any`, `IPv6Any`, `100.64.0.0/10` CGNAT, `192.0.0.0/24`, `198.18.0.0/15`, IPv6 multicast); `TlsHttpHandlerFactory.Create` leaves `SocketsHttpHandler.AllowAutoRedirect` at its .NET default `true`, so a validated host can 302 to an unvalidated one and the filter never re-runs.
- **Verified** (executed): `http://0.0.0.0/x.json` and `http://[::]/x.json` and `http://100.64.0.1/x.json` all passed the filter; separately confirmed `0.0.0.0` really reaches a loopback-bound listener on Linux. A live redirect reproduction through the real `GitLabProvider.DownloadAttachmentAsync` followed a `302` from a validated public path to `/internal-secret.json` and wrote its body to disk.
- **Impact**: security — an attacker-controlled or attacker-editable issue body containing `[x](http://0.0.0.0:PORT/token.json)` or a link that 302s to `169.254.169.254` (cloud metadata) reaches internal/loopback services and gets its response persisted to the workflow's attachment directory and handed to OMP. No provider credential leaks (the untrusted-host header split holds across both hops).
- **Smallest safe correction**: extend `IsUnsafeDestination` with the missing ranges; set `AllowAutoRedirect = false` on the anonymous attachment handler and re-validate each `Location` header manually with a small hop cap.

#### M4-gap-2 — SSRF filter is also vulnerable to DNS rebinding (TOCTOU)
- **Location**: `AttachmentPipeline.IsSafeAnonymousDestinationAsync` performs its own `Dns.GetHostAddressesAsync` for validation; the actual download's `SocketsHttpHandler` re-resolves the same hostname independently at connect time with no `ConnectCallback` pinning the validated address.
- **Verified** by code inspection (security audit + coordinating session); not executed against a live low-TTL DNS server in this pass (would need a controlled resolver).
- **Impact**: an attacker who controls DNS for the attachment host can return a benign address for the validation lookup and a private/loopback/metadata address for the real connect, moments later.
- **Smallest safe correction**: supply a `SocketsHttpHandler.ConnectCallback` for the anonymous attachment client that connects to the exact address `IsSafeAnonymousDestinationAsync` approved, instead of letting the transport re-resolve.

#### L3-gap — Canonical decision list is not round-trip safe: entries are dropped and the next entry is corrupted
- **Spec**: §17 (canonical comment is the durable, in-place-updated authoritative record), §16 ("never omit material decision rationale").
- **Location**: `src/IssueAgent.Context/CanonicalComment.cs` — `Render` (`:38-45`) emits an empty bullet line `"- \n"` for an empty-string decision; `BulletLinePattern` (`:144`, `^-\s+(?<text>.+?)(?=\r?\n-\s|\z)`) has a greedy `\s+` that swallows the following bullet's leading `\n`, and `JoinContinuationLines` (`:146-154`) ends in an unconditional `.Trim()`.
- **Verified independently twice** with identical results (coordinating session's throwaway console app; config/providers audit's separate scratch project):

  | input | rendered | parsed back | round-trips |
  |---|---|---|---|
  | `["First.", "Second.", "Third."]` | ordinary bullets | same | yes |
  | `["Line one.\nSecond line."]` (legitimate multiline) | `"- Line one.\n  Second line.\n"` | same | yes |
  | **`["First.", "", "Third."]`** | `"- First.\n- \n- Third.\n"` | **`["First.", "- Third."]`** | **no — one entry lost, next entry corrupted with a literal `"- "` prefix** |
  | **`["   "]`** (whitespace-only) | `"-    \n"` | **`[""]`** | no |
  | **`["Trailing newline.\n"]`** | — | **`["Trailing newline."]`** | no (trailing newline silently trimmed) |

- **Failure scenario**: OMP's `DecisionsAndRationale` array is not filtered for blank elements anywhere before `Render`. A blank line in the model's own rationale output (plausible — nothing normalizes it) renders, and on the very next read-back (replan, or any subsequent `ImplementationWorkflow`/`PlanningWorkflow` parse of the same comment) permanently loses that decision and corrupts the following one with a leaked `"- "` literal. `Parse` does not throw, so there is no corruption signal, and the corrupted text is what gets re-rendered on the next turn — compounding.
- **Impact**: material decision rationale silently lost from the one authoritative record (§16 forbids this); visibly malformed text published to a public issue comment.
- **Smallest safe correction**: drop empty/whitespace-only decisions at `Render` time so an empty bullet line is never emitted (simplest), or anchor the regex on a single literal space with no greedy `\s+`, and stop unconditionally trimming reconstructed text. Add a regression test for the empty/whitespace-only case — none exists today.

#### New — trust validation runs per inheritance level, so legitimate `§7` inheritance is now a fatal startup error
- **Spec**: §7 ("providers define defaults; repositories inherit and may override"), §31 (invalid configuration is fatal).
- **Location**: `src/IssueAgent.Configuration/IssueAgentOptions.cs` — `ValidateSettings` runs separately on `options.Defaults`, each `provider.Defaults`, and each `repository.Settings`, never on the merged (`EffectiveConfigurationResolver.Merge`) result. This is a regression introduced by this session's M8 fix, which added the pinned-fingerprint-empty check at the per-level validator rather than the merged level.
- **Verified** (executed): global defaults set `git.sshTrust = { mode: pinned, fingerprints: [...] }`; a repository setting only `git.mode: ssh` (intending to inherit the trust policy) fails validation with "requires an explicit host verification policy" even though the *merged* result is valid and has fingerprints. Same pattern reproduced for `git.tls.mode: pinned` set at the repository level while fingerprints live in the shared defaults.
- **Impact**: availability — any operator who factors a shared pinned trust policy into `IssueAgent:Defaults` per §7's own intended pattern gets a fatal, misleadingly-worded startup crash-loop that blames the wrong config level.
- **Smallest safe correction**: run the two git-trust cross-field checks over the merged `RepositorySettingsOptions` per repository (call the resolver's merge from the validator, or relocate the checks into the resolver), keeping only intrinsically-local shape checks (secret-source arity, non-negative numbers) at the per-level validator.

#### M7-gap — effective `targetBranch` is still hardcoded to `"main"`
- **Spec**: §10 ("target branch defaults to the provider default branch, with optional repository override").
- **Location**: `src/IssueAgent.Configuration/EffectiveConfiguration.cs:180` — `var targetBranch = repository.TargetBranch ?? "main";`. Round 1's §11 lists only the `Tls`/`SshTrust` deep-merge half of M7 as fixed; this half was silently dropped from that claim without being flagged as still-open.
- **Verified** (executed) and by code read.
- **Impact**: a repository whose real default branch is `master`/`develop` and that omits `targetBranch` gets `main` resolved at startup; `StartupValidator` swallows the resulting `ResolveBranchCommitAsync` failure into a warning log (readiness stays green), and every subsequent workflow fails silently at base-commit resolution. `tests/IssueAgent.Configuration.Tests/EffectiveConfigurationResolverTests.cs:56` currently *pins* `"main"` as the expected value, actively defending the bug.
- **Smallest safe correction**: add `GetDefaultBranchAsync(RepositoryRef, CancellationToken)` to `IGitProvider` (both Octokit's `Repository.DefaultBranch` and GitLab's `default_branch` already expose it) and resolve the effective target branch at startup when `TargetBranch` is unset; retarget the pinned test instead of leaving it green.

#### M5-gap — attachment fan-out is bounded per comment body, not per workflow context; pagination is unbounded in all four paginating clients
- **Spec**: §15 ("100 MB total per primary workflow context"), §6 ("paginate all eligible issues" under §27's bounded-resource intent).
- **Location**: `AttachmentPipeline.cs:45` — `var attachmentCount = 0;` is local to one `ProcessAsync` call (one comment body), reset every call, despite the omission text claiming "this workflow context". No `MaxPages`/page-count guard exists in any of `GitLabApiClient.GetAllPagesAsync`, `GitHubTimelineClient.GetCrossReferencedIssuesAsync`, or `GitHubGraphQlClient.GetReviewThreadsAsync` — a repo-wide search for `MaxPages`/`pageLimit` returns nothing.
- **Verified** (executed): 4 comment bodies × 5 links each against `MaxAttachmentCount = 5` produced 20 downloads for one workflow context (should cap near 5); 500 zero-byte-response links against a 10-byte total budget produced 500 downloads because the byte budget only rejects non-zero declared sizes.
- **Impact**: an issue with many comments each carrying several direct-file links can drive unbounded outbound requests and local file writes for a single planning turn, exhausting the workspace volume and the provider rate limit while holding a polling slot. Round 1's §11 claimed this bound was added; it was not implemented in any of the four clients, despite `feature-parity-next-block.md:27`/`feature-parity.md:33` remaining `[x]`.
- **Smallest safe correction**: hoist the attachment counter into `RemainingBudget` (or a sibling counter) so it is shared across every `ProcessAsync` call within one context; add a `const int MaxPages` guard to the three unbounded loops, surfacing exhaustion as an explicit omission rather than silent truncation.

#### New — the new global retry policy retries non-idempotent POSTs
- **Spec**: §17 ("one canonical comment"), §27 (retry policy), §25.
- **Location**: `src/IssueAgent.Providers/ProviderRetryPolicy.cs:31-37` — `IsRetryable` returns true for any `>= 500` response regardless of HTTP verb; applied uniformly to `GitLabApiClient.PostAsync` (`CreateIssueNoteAsync`, `CreateMergeRequestAsync`, `CreateLabelAsync`).
- **Verified** (executed): a stub returning `502` then `201` for `CreateIssueNoteAsync` caused the POST to be sent twice, producing two notes.
- **Impact**: a `502` arriving *after* a note was actually created (a common reverse-proxy failure mode) causes a duplicate canonical-comment marker on the issue; `CanonicalCommentLocator`'s M9 uniqueness check then throws `CanonicalCommentCorruptException` on the next dispatch, permanently blocking the issue until a human deletes a comment. Fail-safe (blocked, not silently wrong) but availability-affecting.
- **Smallest safe correction**: retry only idempotent verbs (`GET`/`PUT`/`HEAD`) on `5xx`, or make comment creation idempotent by re-locating the canonical comment before retrying a POST.

#### New — retry delay is server-controlled and uncapped
- **Spec**: §6 (honor `Retry-After`/rate-limit headers), §27 ("3 attempts, exponential backoff, jitter" — implicitly bounded).
- **Location**: `ProviderRetryPolicy.cs:39-55` (`GetRetryDelay` returns the header-supplied delay verbatim when positive) and `GitHubProvider.cs:353-355` (`Task.Delay(exception.GetRetryAfterTimeSpan(), …)`).
- **Verified** (executed): `Retry-After: 999999999` and `X-RateLimit-Reset: 99999999999` both threw `ArgumentOutOfRangeException` from `Task.Delay`'s own argument validation (not a provider error, but tagged as one by the calling decorator); `Retry-After: 3600` produced an hour-long sleep that outlived a 2-second test cancellation token.
- **Impact**: a misconfigured or hostile proxy/header stalls a polling slot for up to an hour, or crashes the call with an unhandled argument exception that surfaces as an opaque provider failure. Defeats §27's bounded-drain intent during shutdown.
- **Smallest safe correction**: clamp the honored delay to a policy maximum (e.g. one minute); treat a larger instructed delay as "do not retry — let the caller reschedule."

#### H6-gap — GitHub retry coverage is 1 of 15 Octokit call sites
- **Spec**: §6, §27 ("one global policy").
- **Location**: `GitHubProvider.cs` — `ExecuteReadWithRetryAsync` exists and is called from exactly one site (`GetIssueAsync`); every other Octokit call (discovery, comments, labels, merge requests — 13+ sites) is a bare `.WaitAsync(cancellationToken)` with no retry/backoff/`Retry-After` handling. GitLab's equivalent surface is fully covered via `ProviderRetryPolicy`.
- **Impact**: avoidable workflow failures on GitHub secondary rate limiting that do not occur on GitLab under identical provider pressure; round 1's §11 claim that "global retry policy covers provider/Git calls" is accurate for GitLab only.
- **Smallest safe correction**: route every Octokit call through the retry helper (a write-safe variant that excludes non-idempotent creates, per the POST-retry finding above).

#### New — canonical comment is not excluded from "human comments"
- **Spec**: §16 ("all human comments chronologically"; bot comments ignored by default), §17, §22.
- **Location**: `src/IssueAgent.Context/AgentContextBuilder.cs:68,146,162` and the equivalent snapshot filters in `ImplementationWorkflow.cs`/`PlanningWorkflow.cs` all filter only on `comment.IsBot`. `CanonicalCommentMarkdown.IsCanonicalComment` exists but is used only by `CanonicalCommentLocator`.
- **Verified** by trace: with `provider-token` auth (§8's normal mode), IssueAgent runs as a PAT-backed user whose login carries no `[bot]` suffix, so `IsBot` is `false` for its own canonical comment on GitHub. (GitLab is better protected — it checks the authoritative `author.bot`/`user_type` fields first.)
- **Impact**: the agent's own full plan text and hidden YAML machine-state block gets fed back into every subsequent prompt as if it were human input; replans partly re-read their own prior output. Not a credential leak (the YAML carries no secrets) but a real prompt-pollution/self-referential-input correctness gap.
- **Smallest safe correction**: add `|| CanonicalCommentMarkdown.IsCanonicalComment(comment.Body)` to every human-comment filter site.

#### New — `ObservableGitProvider.RunEnumerableAsync` mis-measures duration and under-counts requests for paginated operations
- **Location**: `src/IssueAgent.Observability/ObservableGitProvider.cs:186-227` — the stopwatch spans the entire `await foreach` consumption, not just the provider call, and `ProviderRequests` increments once per enumeration regardless of how many HTTP pages the provider issued underneath.
- **Verified** by code read and a `MeterListener` experiment (config/providers audit) confirming exactly one request/duration measurement per enumeration.
- **Impact**: telemetry only, but materially wrong — `issueagent_provider_duration_seconds` for `discover-*` operations includes whatever inline reconciliation/dispatch work the consumer does inside the `await foreach` body (`PollingScheduler.DiscoverRepositoryAsync` runs full `dispatcher.ExecuteAsync` inline for reconciliation-priority candidates), and request-volume metrics under-report by the pagination factor.
- **Smallest safe correction**: measure around each `MoveNextAsync` (accumulate only awaited time) or drop the histogram for enumerable operations in favor of HTTP-boundary instrumentation.

#### New — cancellation is counted as a provider/Git/LFS/OMP error
- **Spec**: §27 (graceful shutdown is normal operation), §30 (alerts should fire on real failures).
- **Location**: `ObservableGitProvider.cs:150-157,174-181,205-212`, `ObservableGitRepositoryManager.cs:79-86,108-114`, `ObservableOmpClient.cs:84-92` — each generic `catch (Exception ex)` increments the error counter before rethrowing; none excludes `OperationCanceledException` (contrast `PollingScheduler.cs:135-138`, which gets this right).
- **Impact**: an `agent:cmd:cancel` or a routine pod rollout increments `issueagent_{provider,git,omp}_errors_total`; the `rate(...[10m]) > 0 for 10m` alert pattern used in `resources.yaml` can page on a single ordinary cancellation.
- **Smallest safe correction**: add `catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested) { throw; }` ahead of the generic catch in every decorator.

#### New — `IssueAgentLongRunningOperations` alert cannot detect the condition it names
- **Location**: `deploy/helm/issue-agent/templates/resources.yaml` — `expr: issueagent_operations_active > 0`, `for: 30m`, while `IssueAgentMetrics.ActiveOperationAge` (exported as `issueagent_operations_oldest_active_age_seconds`) — the metric that actually measures "how long has the oldest active operation been running" — is referenced by no alert and no dashboard panel.
- **Impact**: guaranteed false positives on any agent with continuous 3-minute-average throughput; guaranteed false negatives for one genuinely wedged operation buried among healthy ones.
- **Smallest safe correction**: `expr: issueagent_operations_oldest_active_age_seconds > <threshold>`.

#### New — Grafana "Poll Duration" panel queries a metric series the exporter never emits
